                Arquitectura de Autenticación con Token Opaco, Gateway y JWT

                Arquitectura de Autenticación con Token Opaco, Gateway y JWT

                ¡Va! Te lo explico como arquitecto (AWS + Java) y te dejo diagramas + tips prácticos + fuentes oficiales para cada punto clave.

                Arquitectura (visión general)

                • access-gateway (Spring Cloud Gateway): entrada única; lee la cookie de sesión, valida con identity-service y reinyecta un JWT en Authorization: Bearer ... hacia los microservicios. (Home)
                • identity-service (Spring Boot): valida token opaco con el Authorization Server (introspección), crea sesión en ElastiCache Redis, firma un JWT y setea cookie segura. (IETF Datatracker)
                • utils-service / fraud-ins-service (Spring Boot 3.5.x): stateless; validan localmente el JWT contra el JWKS de identity-service (cacheado). (Home, IETF Datatracker)

                Diagrama 1 — “Handoff”: login vía token opaco (desde app)

                sequenceDiagram autonumber participant App as App origen (ya logueada) participant Browser as Navegador participant GW as access-gateway participant ID as identity-service participant AS as Authorization Server (token opaco) participant Redis as ElastiCache Redis 
                App->>AS: (2.1) Solicita token opaco (con datos del usuario)
AS-->>App: (2.2) token_opaco
App->>Browser: (2.3) Redirige a nueva app: https://newapp/...?token=token_opaco
Browser->>GW: GET /?token=token_opaco
GW->>ID: (3) Enruta a /exchange?token=...
ID->>AS: (4.1) Introspección RFC 7662 (valida token opaco)
AS-->>ID: Respuesta activa + claims del usuario
ID->>Redis: (4.3) Crea sesión (SESSION_ID -> atributos)
ID-->>Browser: (4.4) Set-Cookie: __Host-SESSION_ID=...; HttpOnly; Secure; SameSite=...
Note right of ID: (4.3) También firma un JWT para uso interno
Browser->>GW: (5) Peticiones subsecuentes (cookie incluida)

                Notas clave

                • La validación de tokens opacos se hace con token introspection (RFC 7662). (IETF Datatracker, RFC Editor)
                • Evita que el token viaje mucho tiempo en la URL (logs, referers, history). Si lo usas, que sea de un solo uso y cortísima vida, y haz redirect inmediato a una URL limpia. (Buenas prácticas OWASP sobre query strings sensibles). (OWASP Foundation)
                • Para cookies seguras: Secure, HttpOnly, SameSite adecuado y prefijo __Host- (defensa contra session fixation). Si necesitas cross-site, usa SameSite=None; Secure. (MDN Web Docs)

                Diagrama 2 — Peticiones subsecuentes (propagación de identidad)

                sequenceDiagram autonumber participant Browser as Navegador participant GW as access-gateway participant ID as identity-service participant Biz as Microservicio de negocio participant Redis as ElastiCache Redis 
                Browser->>GW: (5.1) GET /biz/endpoint (Cookie: __Host-SESSION_ID=...)
GW->>ID: (5.1.2) /validate-session (SESSION_ID)
ID->>Redis: (5.1.3) Consulta sesión
Redis-->>ID: OK + info usuario
ID-->>GW: (5.1.3) Responde con JWT firmado (roles, permisos, etc.)
GW->>GW: (5.1.4) Inserta header Authorization: Bearer <JWT>
GW->>Biz: (5.1.5) Enruta con contexto de autenticación
Biz->>Biz: Valida firma y claims del JWT (JWKs cacheado)
                • El gateway puede implementar un GlobalFilter para leer la cookie, llamar a /validate-session y añadir Authorization: Bearer <jwt> antes de rutear. (Home, Baeldung on Kotlin)
                • Los microservicios validan localmente el JWT (firma, exp, iat, iss, aud, scope/roles) apoyándose en Spring Security Resource Server + JWKS (cacheado). (Home)

                Implementación (puntos finos)

                1) Cookie de sesión (HTTP-only, Secure, SameSite)

                Ejemplo de cabecera correcta (ojo: es HttpOnly, no “HTTPonly”, y conviene el prefijo __Host-):

                Set-Cookie: __Host-SESSION_ID=<id>; Path=/; Secure; HttpOnly; SameSite=Lax
                • Strict es muy restrictivo (rompe flujos tipo link-in), Lax suele ser el sweet spot; para cross-site usa SameSite=None; Secure. (MDN Web Docs)
                • Prefijos __Host-/__Secure- endurecen el setting de la cookie a nivel de navegador. (MDN Web Docs)

                2) access-gateway (Spring Cloud Gateway)

                YAML (ejemplo simple de ruta y filtro de cabecera):

                spring:
  cloud:
    gateway:
      routes:
        - id: biz
          uri: http://biz-service
          predicates:
            - Path=/biz/**
          filters:
            - AddRequestHeader=X-Trace-Id, "#{T(java.util.UUID).randomUUID()}"

                (Home)

                GlobalFilter (pseudo-código) para validar sesión y añadir Authorization:

                @Bean
public GlobalFilter sessionToJwtFilter(WebClient.Builder webClient) {
  return (exchange, chain) -> {
    var sessionId = extractCookie(exchange.getRequest(), "__Host-SESSION_ID");
    if (sessionId == null) return chain.filter(exchange);

    return webClient.build()
      .get()
      .uri("http://identity-service/validate-session")
      .header("Cookie", "__Host-SESSION_ID=" + sessionId)
      .retrieve()
      .bodyToMono(String.class) // aquí recibes el JWT
      .defaultIfEmpty("") 
      .flatMap(jwt -> {
        if (!jwt.isEmpty()) {
          var mutated = exchange.mutate()
            .request(r -> r.headers(h -> h.setBearerAuth(jwt)))
            .build();
          return chain.filter(mutated);
        } else {
          return chain.filter(exchange);
        }
      });
  };
}

                Referencias sobre Global Filters y filtros personalizados: (Home, Home, Baeldung on Kotlin)

                3) identity-service

                • Introspección de token opaco (RFC 7662) contra el Authorization Server (/introspect) para confirmar que está activo y leer claims. (IETF Datatracker)
                • Sesión en ElastiCache Redis (TTL acorde a riesgo; usa Spring Session Redis). (Home, AWS Documentation)
                • JWT interno firmado (por ejemplo con RSA/ECDSA). Expón JWKS en GET /.well-known/jwks.json para validación descentralizada. (JWK/JWKS en RFC 7517; la ruta de well-known es la práctica estandarizada por OIDC Discovery). (IETF Datatracker, OpenID Foundation)

                Spring Session Redis (pom y propiedades) — guía oficial: (Home) ElastiCache prácticas (tamaño/escala/cluster-mode y TLS en tránsito): (AWS Documentation, Amazon Web Services, Inc.)

                4) Microservicios de negocio (validación stateless del JWT)

                Config mínima con Spring Security Resource Server (valida firma con tu JWKS):

                spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          jwk-set-uri: https://identity-service/.well-known/jwks.json

                Spring Security auto-configura la validación de Bearer JWT y cachea el JWKS; puedes ajustar caché/timeout si lo necesitas. (Home)

                Sobre el caché del JWKS (Nimbus): por defecto se cachea y se refresca si llega un kid desconocido; puedes tunear TTL (ej. 5–15 min). (javadoc.io)

                Verificaciones recomendadas en tu filtro/interceptor o configuración:

                • Firma (alg, kid) con clave pública correcto.
                • exp, iat, opcional nbf; iss/aud esperado; scopes/roles. (Home)

                5) Seguridad del “token en query param”

                Tu flujo lo usa solo una vez (handoff). Aun así, mitiga:

                • Vida muy corta (segundos), un solo uso, y redirect inmediato a URL limpia.
                • Cache-Control: no-store en respuestas intermedias.
                • Si puedes, usa código de intercambio en lugar de token directamente (patrones de OIDC/BCP). Motivo: la URL puede filtrarse por logs, histórico, Referer, etc. (OWASP Foundation)

                6) Encabezado Authorization: Bearer

                La forma estándar de portar tokens es Authorization: Bearer (RFC 6750). (IETF Datatracker, Swagger)

                AWS (piezas y tips)

                • ElastiCache for Redis como session store (cluster-mode enabled para escalar; definir TTL de sesión). (AWS Documentation)
                • Habilita TLS en tránsito y cifrado en reposo del clúster. (Buenas prácticas generales de ElastiCache). (AWS Documentation)

                Resumen del flujo que pediste (con ajustes recomendados)

                1. Usuario ya autenticado en la app origen.

                2. La app origen obtiene token opaco (RFC 7662), redirige a la nueva app con ?token=... (one-shot, TTL corto; redirect a URL limpia). (IETF Datatracker, OWASP Foundation)

                3. access-gateway detecta el token y enruta a identity-service (endpoint interno de intercambio). (Home)

                4. identity-service:

                  • Introspección del token opaco.
                  • Recupera datos de usuario.
                  • Crea sesión en Redis, firma un JWT, y setea cookie __Host-SESSION_ID (Secure; HttpOnly; SameSite= adecuado). (IETF Datatracker, Home, MDN Web Docs)

                5. Peticiones subsecuentes:

                  • Gateway lee cookie, llama a /validate-session en identity-service, recibe JWT y lo inyecta en Authorization: Bearer. (Home)
                  • Los microservicios validan localmente el JWT (JWKS) y quedan stateless. (Home)

                Enlaces/Fuentes

                • JWT / JWK / JWKS: RFC 7517 (JWK); JWKS autoconsumo vía OIDC Discovery (/.well-known/openid-configuration y jwks_uri). (IETF Datatracker, OpenID Foundation, Auth0)
                • Bearer Tokens (header Authorization): RFC 6750. (IETF Datatracker, RFC Editor)
                • Token opaco / Introspección: RFC 7662. (IETF Datatracker)
                • Spring Security Resource Server (JWT + JWK): docs oficiales. (Home)
                • Spring Cloud Gateway (GlobalFilter / mutate headers): docs + ejemplos. (Home, Home, Baeldung on Kotlin)
                • Cookies seguras (Secure, HttpOnly, SameSite, prefijos __Host-/__Secure-)—MDN: guías y Set-Cookie. (MDN Web Docs)
                • Riesgos de poner tokens en URL (OWASP). (OWASP Foundation)
                • ElastiCache Redis (mejores prácticas; Spring Session Redis). (AWS Documentation, Home)

                Este documento describe un flujo de autenticación basado en token opaco para intercambio inicial, Spring Cloud Gateway como punto de entrada, JWT para propagación de identidad y Redis como store de sesión.

                🔑 identity-service

                • Valida token opaco con introspección (RFC 7662)
                • Crea sesión en Redis (Spring Session Redis)
                • Firma JWT (RSA/ECDSA) y expone JWKS

                application.yml ejemplo:

                spring:
  redis:
    host: localhost
    port: 6379
  session:
    store-type: redis
